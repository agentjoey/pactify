# M2.1 — Cross-Agent Thin Onboarding (MCP-first) — Design

- **Milestone:** Phase 2 / M2.1 (Sprint 003)
- **Date:** 2026-06-10
- **Status:** approved (brainstorm) → ready for implementation plan
- **Depends on:** Phase 1 / Pact-Base complete (protocol v1, `pactify` CLI, `pactify mcp` stdio server)

## Goal

Make any agent — across **both CLI and desktop-app surfaces** — join a repo's pact
with a thin, generated onboarding step, using the MCP server as the primary substrate
and shell as fallback. opencode (CLI) is taken end-to-end and dogfooded; the other
agents are produced from a repeatable per-surface template.

### Decisions locked in brainstorm

1. **Substrate:** MCP-first (`pactify mcp`), shell (`pactify` CLI) as fallback.
2. **Scope:** opencode (CLI) deep + dogfooded; a repeatable template covers the rest.
   Gemini / Codex / Claude get their config wired but are not LLM-verified this milestone.
3. **Delivery:** a `pactify` command auto-wires the agent (writes config + entry block),
   **plus** a generated manual-onboarding doc as fallback/transparency.
4. **Verification gate:** deterministic MCP-level interop test + `pactify mcp` stdio
   smoke test + a `--project` smoke test, all run locally; a real-opencode manual
   dogfood is the exit gate. **No CI workflow this milestone — that is M2.2.**
5. **Both surfaces:** desktop app and CLI are both first-class. Desktop apps use a
   machine-global config and a cwd that is not the repo, so `pactify mcp` gains a
   `--project <dir>` rooting flag.

## Key insight — three orthogonal axes

Onboarding an agent is determined by three independent axes, **not** a single vendor
dimension:

1. **format** — `JSON-mcpServers` / `JSON-opencode` / `TOML` → decides whether we can
   **auto-wire** (JSON: yes; TOML: doc-only this milestone, to avoid a TOML dependency).
2. **scope** — `project` (a file committed in the repo, portable) vs `global` (a
   machine-level file outside the repo) → decides **which path** we write.
3. **rooting** — `CLI` (cwd is the repo, works today) vs `desktop` (cwd ≠ repo) →
   decides whether the MCP invocation needs `--project <abs-repo>`.

"CLI vs desktop" only touches axes 2 and 3. "Can we auto-write it" only depends on
axis 1. So a `surface` is not a special case — it is two parameters.

### Format reference (verified schemas)

- **JSON-opencode** (`opencode.json`):
  ```json
  { "mcp": { "pact": { "type": "local", "command": ["pactify","mcp"],
      "enabled": true, "environment": { "PACT_AGENT_ID": "<seat>" } } } }
  ```
- **JSON-mcpServers** (Claude `.mcp.json`, Gemini `.gemini/settings.json`,
  Claude Desktop, Antigravity `~/.gemini/config/mcp_config.json`):
  ```json
  { "mcpServers": { "pact": { "command": "pactify", "args": ["mcp"],
      "env": { "PACT_AGENT_ID": "<seat>" } } } }
  ```
  Desktop variants add `--project <abs-repo>` to `args`.
- **TOML** (`~/.codex/config.toml` / `.codex/config.toml`) — doc-only:
  ```toml
  [mcp_servers.pact]
  command = "pactify"
  args = ["mcp"]            # desktop: ["mcp","--project","<abs-repo>"]
  env = { PACT_AGENT_ID = "<seat>" }
  ```

## Architecture

### New package `internal/agent`

```go
type Format int   // JSONMcpServers | JSONOpencode | TOML
type Scope  int   // Project | Global

type ConfigTarget struct {
    Path   string   // repo-relative (Project) or absolute/~-expanded (Global)
    Scope  Scope
    Format Format
}

type Invoke struct {
    Command string            // "pactify"
    Args    []string          // ["mcp"] or ["mcp","--project",repoAbs]
    Env     map[string]string // {"PACT_AGENT_ID": seat}
}

type Adapter interface {
    Kind() string
    EntryFile() string                          // "" = pure desktop app, no entry file
    Config() ConfigTarget
    Invocation(seatID, repoAbs string) Invoke   // desktop args include --project repoAbs
}
```

- A **single JSON merger** handles both JSON dialects, parameterized by the parent key
  (`mcp` vs `mcpServers`) and the entry shape (opencode `type/command[]/environment`
  vs mcpServers `command/args/env`). The same merger serves `Project` and `Global`
  paths — only the resolved path differs.
- **TOML kinds** use `Invocation` only for `--print`/doc rendering; nothing is written.
- The onboarding block is one **agent-agnostic "pact briefing"** renderer, parameterized
  by seat id + roles, reusing the existing managed-region machinery in
  `internal/pact/seat.go` (`bakeBlock`, `<!-- pact:begin/end -->`, symlink-safe).

### New engine capability: `pactify mcp --project <dir>`

`pactify mcp` is currently cwd-bound (`paths.Dir()` resolves `.pact` relative to cwd,
and git verbs run in cwd). Desktop apps have a cwd that is not the repo, so they cannot
target a repo today.

`--project <dir>` **chdir-roots** the process to `<dir>` before serving, so that both
`.pact/` resolution and all git operations (join/merge branch ops) are anchored at the
repo. CLI surfaces omit the flag and keep cwd behavior unchanged.

## CLI surface

- **`pactify mcp --project <dir>`** — chdir-root; needed by desktop kinds, harmless for CLI.
- **`pactify agent add <kind> [--id <seat>] [--roles <r1,r2>] [--project <abs>]`**
  - JSON kind → JSON-merge the `pact` server into `Config().Path` (project or global) +
    bake the briefing block into `EntryFile()` if non-empty.
  - TOML kind → does not write; prints the snippet and points at `docs/agent-onboarding.md`.
  - Desktop kind → invocation automatically includes `--project <abs>`; if `--project`
    is omitted it defaults to the absolute path of the current working directory (the repo).
- **`pactify agent add <kind> --print`** — render config snippet + entry block to stdout,
  write nothing. This is the manual path and the data source for the generated doc.
- **`pactify init` 4th seat field** — `--seat 'id:roles:entry:kind'`. Three fields
  (current syntax) ⇒ `shell` kind ⇒ today's behavior, byte-for-byte. Four fields route
  through the adapter.
- **`docs/agent-onboarding.md`** — generated from every adapter's `--print` output
  (JSON kinds listed too, for manual setups). A test asserts the doc matches the
  adapters, so it cannot drift.

## Data flow

```
agent add / init
  └─ resolve Adapter by kind
       ├─ (a) entry  : if EntryFile()!="" → bake MCP-first briefing into managed region
       └─ (b) config :
            JSON kind → JSON merger writes the pact server entry into Config().Path
                        (Project=repo file, Global=machine file; mkdir -p parent)
            TOML kind → print snippet only
```

At runtime the MCP server anchors to the repo (cwd for CLI, `--project` for desktop) and
reads `PACT_AGENT_ID` to fix the seat. **The protocol and engine are otherwise unchanged;**
the only new engine capability is `mcp --project`.

## The pact briefing (shared onboarding content)

One parameterized markdown block, replacing the shell-only block for MCP kinds:

- "This repo uses the pact protocol (v1). You are seat `X`, roles `Y`."
- "**Primary:** the `pact` MCP server is wired into your config — use its tools
  (status / join / assign / checkpoint / accept / changes / merge / list) and resources
  (`pact://state`, `pact://log`)."
- "Cold start: call `status`, then `join` (registers your seat + checks out your feature branch)."
- "**Fallback** (MCP unavailable): `export PACT_AGENT_ID=X; pactify join X --roles Y`,
  then `pactify help`."
- "The two rules: a worker cannot self-accept; a feature cannot merge until all its
  tasks are accepted."

The `shell` kind keeps today's shell-only block verbatim (back-compat).

## Error handling & idempotency

- **Symlink-safe** — reuse `bakeBlock`'s Lstat-remove.
- **JSON merge** — parse existing (missing/empty ⇒ `{}`); **invalid JSON ⇒ error, never
  clobber**; set only the `pact` key under the right parent; preserve sibling servers and
  unknown top-level keys; marshal with sorted keys so a re-run is byte-identical. Applies
  equally to global files (mkdir -p the parent first; a user's other servers must survive).
- **Idempotent** — re-running `agent add` for the same kind/seat produces no semantic
  change; the managed block and the sorted-key JSON are byte-identical on re-run.
- **Unknown kind** — clear error listing the supported kinds.
- **One MCP seat per entry file** — opencode and codex-cli both use `AGENTS.md`, and a file
  holds a single managed block, so two seats sharing one entry file would overwrite each
  other's block. M2.1 supports one MCP-kind seat per entry file (opencode is the deep path;
  codex is doc-only, so the collision does not bite in practice). Multi-seat-per-file
  (seat-keyed managed blocks) is deferred, consistent with the Phase 1 single-worktree limit.

## Testing (verification gate — local only this milestone)

- **Unit (`internal/agent`):** JSON merger across both dialects + project/global paths +
  preserves existing servers + idempotent + symlink-safe; `mcp --project` chdir-roots so
  `.pact`/git resolve at the repo; TOML `--print` snippet is correct; unknown-kind errors.
- **Deterministic interop:** extend M1.3c's in-process MCP client to a full-lifecycle
  scenario — `claude-opus` (orchestrator + reviewer) and `opencode` (worker) switch
  `PACT_AGENT_ID` and drive the **same `.pact/`** through assign → join → checkpoint →
  accept → merge; assert STATE converges and a worker self-accept is rejected. No LLM.
- **MCP stdio smoke:** spawn `pactify mcp` as a subprocess, do a real MCP initialize
  handshake over stdio + `status` + one mutating verb.
- **`--project` smoke:** from outside the repo, run `pactify mcp --project <repo>` as a
  subprocess and drive a verb, proving the desktop anchoring path works.
- **Manual dogfood (exit gate, not automated):** a real opencode CLI wired via
  `pactify agent add opencode` acts as worker end-to-end; the human only says "start".
  Recorded in the Sprint 003 exit notes (as in Phase 0).
- **Baseline stays green:** existing 79 bats + 11 vitest + go test. **No CI workflow —
  M2.2.**

## Scope / YAGNI

**In:** `internal/agent` registry + 8 kinds; JSON merger (two dialects × project/global)
auto-wiring the 5 JSON kinds (incl. two desktop apps); codex (both surfaces) doc-only;
`pactify mcp --project`; `pactify agent add` + init 4th seat field; generated
`docs/agent-onboarding.md`; all of the tests above (local); opencode CLI manual dogfood.

**Out (later milestones):** Codex TOML auto-merge (pulls a TOML dependency — deferred to
when Codex is actually LLM-verified); desktop-app LLM dogfood; multi-worker concurrent
seats / git-worktree isolation (Phase 1 known limit, still deferred); CI workflow +
release pipeline + brew/curl install (all M2.2).
